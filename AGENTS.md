# Работа в проекте ДЕЛО

ДЕЛО — CRM для художественных студий и небольших галерей: занятия, клиенты и картины. Backend — Go, frontend — React/TypeScript; обязательная платформа развёртывания — Kubernetes. Фактическая реализация и ограничения описаны в README.md и docs/implementation-status.md.

## Начало работы и источники требований

- Сначала прочитай запрос пользователя и README.md, проверь фактическое дерево файлов, git status и рабочие заметки текущей задачи. Затем обращайся к подробным документам по необходимости.
- docs/technical-specification.md — основной источник требований. docs/architecture.md и docs/microservices.md описывают архитектуру; docs/kubernetes.md — развёртывание; docs/acceptance-and-decisions.md — решения и приёмку. Прежние предложения архитектуры могут отличаться от текущей реализации: явно указывай расхождения.
- Различай утверждённые требования, предложения и открытые вопросы с пометкой ___. Не выдумывай характеристики оборудования, сроки, метрики, результаты проверок и обязательства. Неизвестные значения требуют согласования или проверки на стенде.
- При изменении требований обновляй затронутые архитектуру, развёртывание и приёмку вместе. Не меняй архитектурные требования молча.

## Общение и стиль

- Пиши по-русски, кратко и по делу. Последовательно объясняй цель, причины и последствия, используй конкретные формулировки, избегай канцелярита и пустых вступлений.
- Доводи порученную работу до проверяемого результата, не расширяй объём без необходимости. Сообщай о противоречиях и предлагай обоснованное решение.
- Если в новом чате переданы только инструкции без задачи, ответь: «Контекст принят. Ожидаю описание изменений». Если задача уже есть, приступай к ней.
- Не создавай PowerShell-файлы (.ps1). Для Kubernetes используй kubectl и YAML; для переносимых проверок — shell или Python.

## Код и обязательные проверки

- Для любого написанного или изменённого кода добавляй или обновляй тесты и запускай их перед передачей результата. Проверяй основное поведение, ошибки и существенные граничные случаи.
- После каждого завершённого изменения кода запускай тесты затронутых компонентов. Перед коммитом выполняй полный доступный набор проверок; единый запуск: TEST_DATABASE_URL=<URL отдельной тестовой БД> sh scripts/check.sh. Конкретные команды и зависимости описаны в README.md.
- Интеграционные тесты выполняй на отдельной PostgreSQL с синтетическими данными. Не используй рабочую БД CRM. Пропуск тестов из-за отсутствия БД не означает успешную интеграционную проверку.
- Backend: go test -count=1 ./... и go vet ./...; frontend: npm test и npm run build. Проверки манифестов: python scripts/check-k8s.py и разбор отдельного demo-admin Job через kubectl. В CI сохраняй обязательные проверки Go с PostgreSQL, frontend, образов и Kubernetes.
- Для CRM проверяй изоляцию организаций и роли; для записи на занятия — одновременные запросы на последнее место; для платежей — повторную доставку событий на тестовых данных. Для входа — форму, неверный пароль, сессию и членство организации.
- Не называй код готовым, если обязательные проверки не выполнены или завершились ошибкой. Указывай точные команды, результаты и ограничения.
- Для изменений только документации проверяй содержание, ссылки, согласованность инструкций и git diff --check; тесты программы без изменений кода не требуются.
- При изменении Kubernetes сверяй локальный профиль, dev, staging и production. Оценки ресурсов и отказоустойчивости подтверждай проверкой на стенде.

## Git и GitHub

- В начале нового чата проверь рабочее дерево, выполни git fetch origin и сравни main с origin/main. Если дерево чистое, перейди на main и выполни git pull --ff-only origin main. Если есть чужие изменения или расхождение истории, сохрани их и выбери безопасный способ работы без reset и удаления. При недоступной сети сообщи, что актуальность main не подтверждена.
- Для новой задачи после синхронизации создавай ветку faust-man/<имя-задачи>. При продолжении текущего чата используй его существующую ветку. Не смешивай несвязанные изменения разных чатов.
- После завершения порции работы и успешных обязательных проверок делай commit и push в ветку текущего чата, затем создавай или обновляй pull request в main. Это относится и к документации. При недоступном push сообщи о локальном коммите и ограничении.
- Изменения main проводи через PR; прямой push в main запрещён. Перед слиянием проверь актуальность веток, отсутствие конфликтов и результаты проверок. После слияния обнови main через git pull --ff-only origin main. Не выполняй force-push и не переписывай чужую историю.
- Перед staging проверь .gitignore и фактический tracking. Добавляй только файлы задачи. Не меняй ignore-правила и не добавляй принудительно исключённые материалы без отдельного указания. Новое правило ignore не удаляет файл из индекса и истории.
- Все компоненты ДЕЛО сохраняй в существующем репозитории https://github.com/faust-man/DELO.git. Не создавай отдельные репозитории. Не меняй видимость репозитория; при создании нового репозитория по отдельному поручению используй private и проверь результат.
- Подтверждай успешный push и адрес репозитория фактическими результатами Git/GitHub. Доступ плагина не означает наличия локальной Git-аутентификации.

## Навыки, заметки и отчёт

- Применяй доступные навыки по смыслу задачи. До первого применения прочитай SKILL.md и сообщи, какой навык используешь. Не выбирай навыки только по совпадению слов.
- Сохраняй полезные промежуточные материалы в work_notes/<задача>/: черновики, решения, вопросы, результаты проверок и краткое состояние со следующим шагом. Не сохраняй внутренние рассуждения, секреты и лишние копии исходных материалов; учитывай ограничения навыков.
- Веди локальный work_notes/отчёт.md: после крупных изменений добавляй дату, выполненные действия, результат, проверки и ограничения. Отделяй факты от планов, сохраняй предыдущие записи. Этот путь уже исключён из Git; перед коммитом проверяй ignore и отсутствие файла в индексе. Не публикуй отчёт и не отправляй его другим людям.
- Решения для команды фиксируй в docs/. Общий контекст должен быть понятен без локальных заметок.
- После изменений пересматривай README.md и обновляй затронутые сведения о структуре, запуске и проверках. Косметические изменения ради изменения не нужны.
