# Аудит безопасности ДЕЛО — 12 ноября 2026

Проверена рабочая копия на основе 3956649 с незакоммиченными изменениями Kubernetes и документации. Это аудит исходников и локальные проверки, не пентест развёрнутого сервиса. Исправления кода не выполнялись. Приоритеты ниже — рекомендации аудитора, не согласованные требования.

## Находки

### SEC-01 — высокая: неавторизованный пользователь может блокировать вход другого

Место: backend/internal/app/app.go:110–117. Счётчик общий для login, увеличивается до проверки пароля, включая успешные входы. После 20 запросов все последующие, даже с верным паролем, получают 429 до конца 15-минутного окна. Для запроса достаточно знать login и публичный Origin; небраузерный клиент может задавать Origin. Атакующий может повторять блокировку каждое окно. Статически подтверждено порядком операций; отдельный HTTP-сценарий атаки не запускался.

Исправление: сочетать ограничение источника и глобальной нагрузки с задержкой для аккаунта; не превращать неверные пароли в безусловную блокировку легитимного входа. Проверить верный пароль после серии неудач, конкурентные попытки и восстановление после окна.

### SEC-02 — высокая: обход ограничения нагрузки сменой login

Место: backend/internal/app/app.go:110–125; backend/db/migrations/0007_login_limits.sql. Каждое новое произвольное имя создаёт постоянную строку login_limits и вызывает дорогостоящую bcrypt-проверку dummyHash. Общего ограничения частоты/числа параллельных bcrypt нет. Ограничение пула БД четырьмя соединениями не ограничивает число проверок пароля после возврата соединения. Нет удаления истёкших строк login_limits. Возможны перегрузка identity и рост БД без аккаунта. Масштаб нагрузки не измерялся; нагрузочная атака не проводилась.

Исправление: ограничить параллельные проверки и общий поток на входе, добавить контролируемый лимит источника и очистку истёкших записей. Проверить множество разных login и поведение при исчерпании лимита. Не доверять произвольному X-Forwarded-For.

### SEC-03 — средняя: выход сообщает успех при неотозванной сессии

Место: backend/internal/app/app.go:153–157. Ошибка DELETE sessions игнорируется, cookie удаляется и возвращается 200. Если удаление не выполнено (например, ошибка БД после успешной проверки токена), копия токена продолжает работать до истечения срока — до восьми часов после входа. Статически подтверждено; сбой БД не инъецировался.

Исправление: проверять результат удаления, возвращать ошибку отзыва и регистрировать сбой без токена. Добавить тест ошибки удаления и повторного использования токена.

### SEC-04 — средняя: единый доступ модулей к данным увеличивает последствия компрометации

Место: backend/internal/servicehost/server.go, backend/internal/app/app.go:387–396, infra/k8s/base/services/*/resources.yaml. Модули получают общий DATABASE_URL из delo-runtime; разделения ролей БД по сервисам и RLS в миграциях нет. Проверки org выполняет приложение. При компрометации одного модуля общие права БД позволяют выйти за границы его HTTP-маршрутов и организации. Это архитектурный риск с условием компрометации, не найденный обход авторизации обычным HTTP-запросом. Фактические привилегии production-роли неизвестны; наличие superuser у runtime не утверждается.

Исправление: отдельная роль миграций и минимальные права runtime, затем права по сервисам; защиту организаций на уровне БД проектировать отдельно. Согласовать с docs/architecture.md и docs/microservices.md перед изменением архитектуры.

## Условия локальной поставки

HTTP, COOKIE_SECURE=false и явный demo-admin с известным паролем разрешены документацией только локально. Это не скрытая уязвимость, но такую конфигурацию нельзя публиковать в сеть. APP_ORIGIN не валидируется при старте: пустое значение допускает POST без Origin; неправильная настройка ослабляет заявленную проверку. Перед внешним размещением нужны HTTPS, Secure cookie, валидированный Origin и исключение демо-учётных данных. Production-поставка заявлена как нереализованная; сертификаты, ingress, CNI enforcement, резервные копии, реальные права БД и секреты кластера не проверялись.

## Что проверено и работает

Сервер проверяет членство и роли, использует параметризованные значения SQL и список разрешённых таблиц; составные внешние ключи включают org. Сессии хранятся в виде SHA-256 токена, cookie HttpOnly/SameSite=Strict. Запрос ограничен 64 KiB. Для команд есть транзакция, повторная проверка прав, идемпотентность и аудит. Эти меры снижают риск; отсутствие найденного обхода не доказывает отсутствие всех уязвимостей.
