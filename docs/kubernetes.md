## 3. Отказоустойчивость и размещение

Предлагается минимум три worker-узла в трёх зонах. Реплики API/web/worker распределяются по hostname и доступным зонам через topologySpreadConstraints; допустимый skew и режим при нехватке зон ___ согласуются с инфраструктурой. Для узлов и обновлений оставляется запас N+1 и место под maxSurge. Проверяется, что потеря одного узла/зоны не оставляет единственную БД, gateway или доступ к томам.

Для stateless Deployments предлагаются RollingUpdate maxUnavailable=0, maxSurge=1; PDB minAvailable=1 при исходных двух репликах. Конкретные значения зависят от SLO и ёмкости. PDB ограничивает добровольные вытеснения и не гарантирует защиту от аварии узла; rollout управляется стратегией Deployment отдельно. Эти ограничения подтверждаются [официальной документацией о disruptions](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/).

API на SIGTERM перестаёт быть ready, завершает принятые запросы в пределах terminationGracePeriodSeconds ___, закрывает соединения; gateway учитывает drain. У worker прекращается получение новых задач, текущая завершается или lease истекает для повторного исполнения. Длительность внешних вызовов/lease/завершения согласуется, финансовая операция после SIGTERM не повторяется без сверки.

Probes: startup — успешная инициализация, readiness API — возможность обслужить бизнес-запрос с необходимой БД, liveness — жив процесс/цикл без зависимости от внешнего SMS/платёжного сервиса. Для worker проверяются heartbeat/работоспособность цикла; ошибки отдельного провайдера не должны перезапускать все worker. Пороги, интервалы и таймауты ___ определяются на стенде, чтобы не создавать restart storm при кратком сбое БД.

Необходимо проверить отказ control plane, LB/gateway, DNS, CNI и зоны. Поднятие новых Pod невозможно без работоспособных зависимостей платформы; продолжение уже запущенного приложения не означает возможность его масштабирования. Для каждого отказа указывается допустимая деградация, время обнаружения и восстановления ___.

## 4. Масштабирование и пределы роста

API масштабируется HPA по CPU и, после подключения адаптера, метрикам RPS/latency/in-flight. Worker — по возрасту/глубине очереди и времени обработки; CPU остаётся вспомогательным сигналом для IO-bound задач. Для CPU-utilization HPA задаются корректные requests, требуется рабочий pipeline метрик. Custom metrics требуют соответствующего API/адаптера. Это следует из [контракта HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/); выбранные сигналы и пороги — решение проекта.

Предлагаются запрет scale-to-zero для web/API/основных worker и окно стабилизации scale-down; значения ___. Autoscaler узлов или эквивалент провайдера подключается отдельно: HPA создаёт спрос на Pod, но не создаёт физическую ёмкость самостоятельно. Для минимального набора обеспечивается зарезервированная ёмкость, а стоимость и максимальный размер node pool ограничиваются квотой ___.

Каждый workload получает requests CPU/memory, memory limit и согласованный CPU limit с проверкой throttling. Worker для PDF/изображений отделяется, если его пиковая память мешает API. Ограничиваются concurrency, размер тела, время запроса, открытые соединения, количество заданий одного tenant и скорость вызовов провайдера. Tenant-лимиты хранятся согласованно, а не в памяти каждой реплики.

Бюджет БД: сумма `(max API replicas × API pool) + (max worker replicas × worker pool) + миграторы + резерв администрирования` не превышает согласованный лимит PostgreSQL/пулера. Значения ___; PgBouncer/аналог ___ вводится с проверкой совместимости транзакций и prepared statements. HPA ограничивается этим бюджетом. Для больших импортов используются порции/отдельные очереди, backpressure и лимиты, чтобы не блокировать кассовые операции.

Порядок увеличения мощности: измерение медленных запросов и блокировок → индексы и запросы → ресурсы/пулы → независимые worker → read replica для допускающих отставание отчётов → разбиение больших исторических таблиц при доказанной необходимости. Платежи, остатки посещений и custody читаются с primary для строгих решений. Кеш/реплика не принимают окончательное решение о доступности. Брокер, Redis и выделенные микросервисы добавляются по метрикам; конкретные пороги и условия ___ фиксируются ADR.

При выделении сервиса сначала определяются владелец данных, версия контракта, схема событий, идемпотентность, миграция и компенсации. Распределённые транзакции не возникают автоматически из переноса Go-модуля в отдельный Deployment. На первом этапе согласованная транзакция PostgreSQL сохраняется.

## 5. PostgreSQL, S3 и постоянные данные

Kubernetes управляет приложением; сервисы данных могут находиться вне кластера по закрытой сети. Для production предпочтительны managed HA PostgreSQL с автоматическим failover, PITR/WAL и управляемое S3 с versioning/защитой удаления. Провайдер и контрактные показатели ___; исходный лимит NFR-02 не доказывает возможности выбранного сервиса.

Если требование полного self-hosted размещения будет подтверждено, PostgreSQL разворачивается оператором ___: предлагается primary + две standby в разных отказных доменах, контролируемое переключение, fencing старого primary, пулер и независимые копии. Режим synchronous/asynchronous и выбор между доступностью и потерей последних транзакций ___ должны соответствовать согласованному RPO. S3 — распределённое решение/оператор ___ с количеством узлов/дисков по его требованиям. Один StatefulSet с одним диском не заменяет отказоустойчивое хранилище.

Для persistent workloads задаются StorageClass/CSI, допустимые зоны, access mode, reclaimPolicy, объёмы/IOPS, расширение и мониторинг заполнения ___. Поведение при потере зоны и возможность подключения/восстановления тома тестируются. PVC не считаются независимой резервной копией, snapshot сам по себе не доказывает application-consistency. Kubernetes StatefulSet предоставляет идентичность/привязку storage, но репликация и backup определяются отдельно — [официальное описание StatefulSets](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/).

Прикладные Pod не хранят единственную копию данных в emptyDir/root filesystem. Временные файлы ограничены размером и очищаются; завершённые документы и оригиналы — в S3, metadata/checksum/version — в PostgreSQL. Загрузка: создание pending metadata → выдача ограниченной upload-сессии → проверка существования/размера/checksum → scan → ready. Незавершённые объекты очищаются по retention ___; сбой не создаёт «готовый» документ без файла. БД и объектное хранилище не имеют общей ACID-транзакции, используется явный workflow с повтором/сверкой.

## 6. Сеть, TLS и доступ к данным

Внешний доступ — только HTTPS через LB/gateway. Same-origin маршруты: `/` → web, `/api/v1` → API. Отдельные timeout/body limits для upload/webhook задаются явно ___; private bucket выдаёт presigned URL с ограниченным сроком, разрешённым CORS и проверенной областью доступа. Для файлов возможно прямое TLS-соединение с S3, поэтому его домен и политика доступа также согласуются. PostgreSQL, metrics, debug и Kubernetes API не публикуются в интернет без защищённого административного контура.

NetworkPolicy по умолчанию запрещает вход/выход; явно разрешены gateway→web/API, API/worker→БД/S3/секреты/провайдеры, DNS, мониторинг. Платформенные зависимости сертификатов и secrets-оператора учитываются отдельно. CNI должен исполнять политики; наличие YAML без поддерживающего сетевого плагина недостаточно. Стандартная NetworkPolicy не является универсальным FQDN/HTTP firewall, правила внешнего egress обеспечиваются CNI/egress gateway/сетевыми средствами провайдера ___. Ограничения описаны в [документации NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/).

TLS защищает внешний трафик и соединения с data services согласно их поддержке; необходимость service-to-service mTLS внутри кластера ___ определяется моделью угроз. Service mesh не обязателен до подтверждённой задачи. Внутренние сервисы используют ClusterIP; административный доступ через VPN/SSO/защищённый bastion ___ с аудитом.

## 7. Секреты, RBAC и политики контейнеров

Источник секретов — внешний secret store ___; доставка через согласованный оператор/CSI/workload identity. В values и Git хранятся ссылки, не открытые токены. Kubernetes Secrets не считаются шифрованием только из-за base64; требуется защита at-rest и RBAC. Это ограничение зафиксировано в [документации Secrets](https://kubernetes.io/docs/concepts/configuration/secret/). Ротация ключей проверяется без потери действующих сессий, а компрометация допускает их принудительный отзыв.

Каждому типу Pod — отдельный ServiceAccount; automountServiceAccountToken отключён, если Kubernetes API не нужен. Runtime API/worker имеют ограниченные роли БД без DDL; migrator — отдельную identity. RBAC оператора, CI/GitOps и аварийного администратора разделяется. Break-glass доступ выдаётся на срок ___ с журналированием и последующим отзывом. Доступ tenant-клиента в Kubernetes не предоставляется.

Production namespace использует Pod Security restricted либо согласованный эквивалент. Контейнеры: runAsNonRoot, readOnlyRootFilesystem, allowPrivilegeEscalation=false, drop capabilities, seccomp RuntimeDefault; writable tmp — ограниченный volume. Привилегированные platform-компоненты находятся в отдельной области и проходят отдельное согласование. Запрещены latest/unpinned tags и hostPath для бизнес-данных. Admission проверяет обязательные labels, requests/limits, подпись/digest, допустимые registry и отсутствие публичной публикации внутренних сервисов. Конкретный policy engine ___, правила проверяются в CI и кластере.

## 8. Поставка, Helm и GitOps

Стандартный маршрут: разработка → review → CI → registry по digest → staging values → sync → migration Job → rollout → smoke/E2E → изменение production values по правилам ___ → sync → наблюдение за SLO. Предлагается Helm + Argo CD. Для одного ресурса есть один владелец применения; ручной kubectl edit запрещён как штатная поставка, аварийное изменение обязательно возвращается в Git с причиной.

Helm chart содержит Deployment/Service web/API/worker, ConfigMap, ServiceAccount, RBAC, HPA, PDB, NetworkPolicy, Gateway/HTTPRoute при выбранной области владения, миграционный Job, служебные CronJob и monitoring-объекты при наличии CRD. GatewayClass, CNI, CSI, secrets controller, metrics adapter и операторы данных устанавливаются платформенным слоем, а не дублируются каждым release приложения. values.schema.json запрещает неполные production-параметры; безопасная базовая values не маскирует отсутствие настройки HA.

Предлагаемый порядок GitOps: platform CRD/controllers → namespaces/policies/identity → данные/секреты и проверка доступности → versioned migration Job → Deployments/Service/routes → smoke Job. Порядок и health checks реализуются выбранным механизмом синхронизации; поведение Helm hooks внутри GitOps проверяется отдельно, нельзя полагаться на совпадение семантики всех инструментов.

Миграционный Job имеет имя по ревизии, DB advisory lock, deadline, backoff и отдельную роль. Повторная синхронизация безопасна. После failure rollout прекращается; существующие совместимые Pod продолжают работать. Миграция не выполняется из initContainer каждой реплики. Схема expand → совместимый код → backfill с наблюдением → contract отдельным релизом. Откат кода не запускает автоматический разрушительный down.

Frontend и API поддерживают старый UI в пределах окна кеширования ___; OpenAPI и изменения DTO проходят compatibility check. Статические файлы старой ревизии доступны в согласованное окно ___, чтобы открытая вкладка не ломалась после rollout. Конфигурация среды frontend подаётся безопасно через runtime config, без секретов; либо фиксируется отдельная сборка среды ___ с контролем provenance.

CI дополнительно проверяет Helm render для каждой среды, schema validation по закреплённой версии Kubernetes/CRD, admission policies, deprecated API, отсутствие секретов, smoke в временном kind-кластере и staging. Для production учитывается HPA-владение replicas: GitOps не должен постоянно возвращать масштаб к статическому значению; конкретное правило поля и chart описывается до запуска.

## 9. Планировщики, очереди и служебные задачи

Бизнес-таймеры с требуемой точностью — lease-задачи в PostgreSQL и Go worker. Каждый запуск имеет бизнес-ключ и транзакционную защиту; две реплики worker допустимы без единственного незаменимого scheduler. CronJob используется для запуска согласованных maintenance-команд, с timezone, startingDeadlineSeconds, concurrencyPolicy, activeDeadlineSeconds, backoffLimit и history limits ___.

CronJob допускает пропуски/повторы при определённых условиях, поэтому команды идемпотентны; concurrencyPolicy не заменяет межзаданийную блокировку. Эта семантика описана в [документации CronJob](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/). Неуспешная очистка не препятствует приёму оплаты, а недоступность backup создаёт критичное оповещение согласно порогу ___.

Копирование managed БД выполняет провайдер; CronJob может проверять его состояние, а не создавать второй несогласованный процесс backup. В self-hosted профиле копирование/PITR организует оператор или специализированное средство. Дедупликация и сверка платежей обязательны независимо от числа Pod и механизма расписания.

## 10. Наблюдаемость и ёмкость

Метрики приложения и инфраструктуры объединяются по environment/cluster/service/version, без ФИО, телефонов и неограниченных tenant/user labels. Нужны dashboards: успешность/latency операций, outbox age, платёжные processing, просрочки передач, HTTP saturation, DB pool/locks/replication lag, Pod readiness/restarts/OOM, pending Pod, node/disk pressure, PVC growth, backup age и certificate expiry.

Предлагаемый стек: Prometheus-совместимые метрики, Grafana, централизованные логи и OpenTelemetry traces; реализации ___, retention ___, бюджет ___. Внешняя проверка доступности находится вне production-кластера, критичные оповещения не зависят только от упавшей системы мониторинга. Для managed control plane измерения согласуются с доступной телеметрией провайдера.

Для целей доступности предлагается исходный SLO 99,9% в месяц для согласованного набора основных операций; утверждённый SLO ___, исключения/окна ___, error budget и правила остановки релизов ___. Фоновая доставка имеет отдельный SLO по возрасту задания ___, восстановление — отдельные RPO/RTO. Метрика «Pod running» не подтверждает бизнес-доступность.

Нагрузочный профиль содержит tenants, concurrent users, операции/сек, размер истории и файлов, частоту отчётов, импорт и webhook burst ___. Проверяются штатная нагрузка, пик, один недоступный узел и concurrent background jobs. Результат определяет node pools, HPA max, pool БД, лимиты и стоимость. Маркетинговое обещание «большая система» не заменяет измеримый capacity plan.

## 11. Backup и восстановление

Целевое предложение для HA-профиля: БД RPO ≤ 15 минут, RTO основной системы ≤ 60 минут при согласованном сценарии аварии; для файлов RPO ___ и политика согласованного среза ___. Полная потеря региона/провайдера может требовать другого RTO ___ и warm-резерва. Окончательные показатели и бюджет ___. Если инфраструктура их не обеспечивает, это отклонение от целевого профиля, а не скрытое уменьшение требований.

Состав: SQL base backup + WAL/PITR; оригиналы/версии S3; metadata о версиях/checksum; ссылки и доступ к ключам; IaC/GitOps; политики/CRD/версии операторов; registry/artifact mirror согласно сроку хранения ___. Копии и ключи защищены от удаления вместе с основным кластером/аккаунтом; отдельный отказный домен и credentials ___. Снимок etcd не заменяет backup БД/S3.

Порядок восстановления: изолировать старый writer/fence → создать инфраструктуру и платформу → восстановить identity/секреты → БД на выбранный момент → необходимые версии объектов на согласованный срез → проверить ссылки/балансы/custody → запустить совместимую ревизию в ограниченном режиме → сверить платежи/возвраты с провайдерами за окно аварии → разрешить worker и внешние отправки → переключить DNS/gateway → smoke и контроль → протокол. Повтор уведомлений, webhook и обработка outbox после PITR учитываются как отдельный риск; внешний платёж мог состояться после восстановленного среза БД.

До первого production — полное восстановление в чистый кластер. Далее предлагаются ежемесячная проверка восстановления данных и ежеквартальная проверка полного DR; точное расписание ___, ответственный ___. Тест измеряет время, полноту объектов, согласованность денег/посещений/местонахождений и изоляцию, а не только старт Pod.
